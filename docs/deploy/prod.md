# Выкладка на vilax.ai (этапы 13–14, вариант А)

Сайт лежит на том же сервере, что и платформа, но в своей папке: `/opt/vilax-site/releases/<коммит>` и ссылка `/opt/vilax-site/current`. nginx отдаёт vilax.ai из `current`. Выкладка и откат переключают ссылку. Релиз платформы, reload nginx и права root для этого не нужны. Хранятся 5 последних релизов.

Путь на прод утверждает владелец сервера (Р-2). Без реквизитов юрлиц в подвале и политиках на прод не выходим (Р-12).

## Команды

| Что | Команда |
|---|---|
| Показ: что в main, что отдаёт vilax.ai, что на сервере (ничего не меняет) | `bash deploy/site-release.sh` |
| Репетиция: все проверки и пакет, без сервера | `bash deploy/site-release.sh <коммит> --build-only` |
| Выкладка коммита из main | `bash deploy/site-release.sh <коммит>` |
| Откат за секунду на прежний релиз | `bash deploy/site-release.sh rollback` |
| Откат на названный релиз | `bash deploy/site-release.sh rollback <коммит>` |
| Релизы, current, журнал | `bash deploy/site-release.sh status` |
| Разовая настройка сервера (печатает, ничего не делает) | `bash deploy/site-release.sh setup` |
| Снимок боевого сайта «как до выкладки» (только GET) | `bash deploy/check-prod.sh snapshot <папка>` |
| Проверка после выкладки по снимку | `bash deploy/check-prod.sh after <папка>` |

Настройки берутся из окружения или из `deploy/.env.release`. Этот файл в git не попадает.

| Переменная | Что |
|---|---|
| `VILAX_SITE_SSH` | пользователь@сервер для выкладки; выдаёт владелец сервера |
| `VILAX_SITE_ROOT` | папка сайта на сервере, по умолчанию `/opt/vilax-site` |
| `PUBLIC_VILAX_YM_ID` | номер счётчика Яндекс Метрики (Р-11); пусто — Метрики нет |
| `VILAX_PROD_SNAPSHOT` | папка снимка «до» — тогда проверка «после» идёт сама |

## Что делает выкладка

1. Берёт коммит только из `main` и выгружает его в чистую временную папку.
2. Гоняет `npm run check` и тесты комплекта (`deploy/tests`).
3. Собирает prod: `VILAX_MODE=prod`, адрес приёмника `https://tracker.vilax.ai/api/site/demo-request`, Метрика — если задан номер. Кладёт `version.json` с коммитом.
4. Ставит CSP с хэшами встроенных скриптов в каждую страницу (`deploy/csp.mjs`).
5. Проверяет папку (`deploy/check-dist.mjs --mode prod`): форма шлёт только на приёмник, нет noindex, нет адресов стенда, robots и sitemap на vilax.ai, правовые страницы со словами, на которые опираются плагин и приложения, нет лишних файлов и `.well-known`.
6. Открывает сборку в headless Chrome (`deploy/smoke.mjs --mode prod`). Форма не отправляется: это боевая CRM.
7. Пакует, передаёт на сервер, сверяет sha256. Серверная часть (`deploy/server/site-remote.sh` из того же коммита) раскладывает релиз, проверяет состав, переключает `current` и хранит 5 релизов.
8. Если nginx уже смотрит в `current`, сервер сверяет, что отдаётся именно этот коммит. Иначе ссылка сама возвращается на прежний релиз.
9. Локально проверяет `https://vilax.ai/version.json` и, если задан снимок, проходит `check-prod.sh after`.

Перед выкладкой — тяжёлая работа на 3–5 минут (проверки, сборка, Chrome).

## Первый запуск (ворота 3)

1. Владелец сервера разово создаёт пользователя и папки (`bash deploy/site-release.sh setup`) и выдаёт `VILAX_SITE_SSH`.
2. Снимок «до» прямо перед запуском: `bash deploy/check-prod.sh snapshot <папка>`.
3. `bash deploy/site-release.sh <коммит>` — файлы разложены, nginx пока отдаёт прежний лендинг.
4. Владелец сервера правит `vilax-ai.conf`: `root /opt/vilax-site/current`, настоящий 404, www → vilax.ai, заголовки безопасности и кэша. Блок AASA не меняется. Затем `nginx -t` и reload. Черновик правки передан ему отдельно — в нём конфиг платформы, в этот репозиторий он не кладётся.
5. `bash deploy/check-prod.sh after <папка>` — пять пунктов «Проверки после выкладки» из ТЗ и сверка со снимком. Ответ AASA должен совпасть байт в байт.
6. Руками: вход по Face ID в приложении на iPhone; одна настоящая заявка с vilax.ai доходит до CRM и группы, затем её обезличивают.

## Откат

- Релиз сайта: `bash deploy/site-release.sh rollback` — ссылка на прежний релиз, одна секунда, без reload nginx.
- Полный возврат к прежнему лендингу: владелец сервера возвращает `root /opt/vilax/current/landing` и делает reload. Старый лендинг не удаляется, пока новый сайт не проработает месяц.
- Заявки: выключить приём в трекере (`vilax-team section sitelead off`), сайт покажет запасной контакт.

## Что нужно на машине, откуда выкладывают

Node 24 и `npm ci` в рабочей копии, Chrome (или `CHROME_PATH`), ssh/scp, curl, tar. На сервере — bash, tar, sha256sum, flock, curl (есть в Ubuntu).
